01 / THE PROBLEM

Why does searching matter?

New York City has a very large number of parking and camera violation records. Finding one summons number can require many checks if the data is not organized for searching.

THE CHALLENGE

Large amounts of information

Imagine looking for one ticket in thousands or millions of records. A basic method may need to inspect records one by one.

THE QUESTION

Can we search more efficiently?

This project tests three algorithms on the same search task and compares their work, runtime, and memory requirements.

02 / THE DATASET

Real information from NYC

The project uses the official Open Parking and Camera Violations dataset from the NYC Department of Finance.

OFFICIAL PUBLIC DATA

Open Parking and Camera Violations

Dataset ID: nc67-uf89. Fields used include summons number, issue date, violation description, fine amount, amount due, state, and precinct. The source is very large; this project downloads a smaller reproducible sample instead of committing the full dataset.

04 / THE ALGORITHMS

Three ways to find one record

Each method solves the same problem but uses a different strategy.

O(n)

Linear search

Checks records one at a time until the target is found or the list ends. Works even when records are unsorted.

Best for:

Small or unsorted lists.

O(log n)

Binary search

Checks the middle item and removes half of the remaining search area. The list must be sorted first.

Best for:

Sorted lists and repeated searches.

O(1) average

Hash-table search

Uses a dictionary to map each summons number to its record. Building the index requires extra time and memory.

Best for:

Many lookups after indexing.

Fair comparison: report sorting time and hash-index construction time separately from lookup time. Setup is not free.
05 / COMPLEXITY

What Big-O tells us

Big-O describes how work grows as the number of records increases. It does not predict an exact number of seconds.

AlgorithmBestAverageWorstExtra space
LinearO(1)O(n)O(n)O(1)
Binary (iterative)O(1)O(log n)O(log n)O(1)
Hash lookupO(1)O(1) averageO(n)O(n) index

n is the number of records. Hash-table worst-case lookup can be O(n); building the dictionary takes expected O(n) time and O(n) space.
